## 客户端资源定位

Windows 同机加载本地 VPK 绝对路径成功；该路径不能直接当作跨平台 addon 名。Ubuntu run04 使用正确 VPK，但客户端收到 Linux 绝对路径后提示路径无法正确组合，随后因 duplicate assigned ability id 3060 崩溃，服务端未达到 FULL。崩溃转储已提取错误与 addon 路径；不能把这一轮记为正常进房。

改为两端 dota_addons 中唯一同名 d2core_m0_3564393242.vpk 后，两次跨机进房通过。服务端为私有目录中指向上传 VPK 的链接，客户端为已核验的同字节副本。客户端另有历史纯数字 ID 的目录链接和不同哈希的创意工坊包；本次未覆盖它们，也未证明崩溃时具体读取了其中哪一个。

M1 模板与接入文档必须区分“服务端实际资源路径”和“发送给客户端的 addon 标识”。资源分发仍属于上层，核心不更新玩家资源。唯一名称与哈希核验是本轮复验方法，不擅自将固定地图 ID 写成产品限制。

## 端口与状态边界

| 类型 | 实际观测 | 实现约束 |
| --- | --- | --- |
| 游戏端口 | 双平台均绑定相同数值的 UDP 和 TCP；Windows -ip 回环仍出现 UDP 全地址，Ubuntu TCP/UDP 全地址 | 显式端口同时检查 TCP/UDP，不把 -ip 当作隔离保证；检查后仍存在外部抢占竞态 |
| 附加监听 | 每个引擎有一个动态回环 TCP 监听；具体用途未确认 | 记录归属与实际端口，不当作第二个公网游戏端口，不声称已验证关闭它 |
| 对外连接 | 最终 Ubuntu 轮 ss -antup 记录多个出站 TCP 临时端口 | 不把出站临时端口作为核心静态预约端口；仍需纳入诊断快照 |
| 公网 | 本次用户只配置 UDP 游戏端口映射，实际进入两次 | 不要求凭空新增 TCP 公网映射；不承诺所有地图或协议都不需要它 |

ss_active 单独不能判就绪：run03 已 active 但地图主脚本失败。M1 本测试模板采用本代日志中的地图加载、Host activate、地图 command-ready 与进程仍存活的组合，并要求没有已识别加载失败；记录证据时间、代次、来源与适用地图。缺少地图级正面证据保持加载/未知，不靠固定等待几秒或旧日志推断。客户端实际进房仍是验收证据，核心不冒充自动完成玩家进房。

启动观察上限初值 120 秒，优雅停止 10 秒、强制后确认 5 秒，均做成可配置值。这些是基于本轮数秒至十余秒启动、亚秒正常停止留出余量的工程初值，不是统计分位或任意机器保证。超时后按任务书报告失败并尝试停止；未确认退出不释放分配、不启动下一代。

## 失败、编码与权限

| 实验 | 结果 / 处置 |
| --- | --- |
| Windows UDP 冲突 | 独占绑定探针拒绝，未写 intent、未启动引擎；TCP 也进入预检 |
| Windows cfg 已存在 | 拒绝覆盖，未启动引擎 |
| Windows 日志不可写 | 首次 ACL 设置被沙箱拒绝且脚本错误地继续，导致一次测试进程启动：保留失败记录，已按身份正常退出；修正为设置失败立即停止后，宿主复验成功，在启动前拒绝写入，无引擎进程 |
| Ubuntu 日志不可写 | run07 引擎能存活但无引擎日志，stdout 不能替代完整日志；修正探针，run11 以实际 dota 身份预开日志失败，未 exec 引擎 |
| 无效地图 | Windows ASCII 空格路径轮与 Ubuntu run09 均有加载失败、回到 Idle 的日志；进程存活不是加载成功 |
| 默认 cfg 被遮蔽 | Ubuntu run01 崩溃；私有目录补齐明确的 10 个 stock .vcfg 后解决，未复制生产房间 cfg |
| 地图布局 | Ubuntu run02 pak01 目录布局失败；run03 解包 CRC 通过但主脚本失败，根因未定；最终使用原始 VPK，未改地图代码 |
| 英文空格路径 | Windows 安装路径、双平台引擎日志路径均已实际使用成功 |
| 中文路径 | Windows 中文空格引擎日志为空；Ubuntu 中文空格、纯中文目录均未创建引擎日志，目录权限已验证可写。不是日志内容编码测试 |
| 中文内容 | Windows 成功轮 14 条、Ubuntu 成功轮 18 条完整包含中文玩家名；UTF-8 读取无替换字符 |

用户在确认中文玩家名正常记录后，接受引擎日志路径使用 ASCII 字符（允许空格）。探针已在启动前明确拒绝非 ASCII 日志路径，不改写到其他目录。该限制应进入 M1 静态校验与说明；没有证据据此宣布所有中文资源路径都失败，也不承诺未测路径可用。

## 平台实现选择与后续验证责任

- 固定开发工具链 Go 1.27.1，当前 Go 验证工具无第三方依赖。PowerShell 7 / Python 3.12 是本轮实验工具，不是最终用户安装前提；M1 将平台 API 整理进 Go。
- Windows 使用独立控制台、明确 argv、持有进程句柄后核验路径/创建时间；优雅退出通过小型独立辅助进程连接目标控制台并发送 quit，拒绝共享控制台；强制停止仍用已核验句柄。不能使用随管理端句柄关闭而杀游戏的 Job 选项。
- Linux 正常退出采用独立 FIFO，记录后重新打开；强制信号采用 pidfd，结合 boot ID/start ticks/argv 核验，拒绝退化成只按 PID 杀进程。当前 Ubuntu systemd 单元提供生产共机测试隔离和有界资源；并未验证普通用户直接启动 Go 管理端的完整部署流程，不将 root/systemd 变成未经用户确认的产品必需条件。M1 的真实 Go 启动适配必须复验相同生命周期，M0 的系统工具结果不等于该适配已完成。
- 本地传输选择 Windows 当前用户 ACL 的命名管道、Linux 0700 私有目录中的 0600 Unix socket，并校验 peer UID；Windows 实际 CurrentUserOnly 往返通过，Linux 同用户往返与 nobody 拒绝通过。Windows 首个 PowerShell 管道探针曾同步等待不返回，已结束；改成明确缓冲、有界异步读写后通过。M1 需在原生实现加拒绝远程管道连接和超时，测试跨用户访问、端点抢占、长路径，不能从当前探针直接推定完整协议安全性。
- 管理端离线时，引擎直接写本代日志，不依赖管理端 stdout 管道。管理端只能对自己在线时的读取/轮转负责；离线容量控制尚未实现，M3 必须固定边界，不声称已有硬上限。
- 缺失身份记录时，先找到并核验唯一候选；不明确则保留未知并禁止重复派生。M0 已验证该机制可行，M2 才实现持久化恢复表、创建幂等和所有崩溃窗口。

未执行且不标通过：整机重启实测、PID 重用压力实验、任意地图/架构、共享安装多实例并发、长时间容量、A2S 改动后的组合复验、正式 Go 管理端闭环。它们分别由 M1 的实现回归、M2 的可靠性和 M3/M4 的范围承接；本次不改变相应交付要求。
