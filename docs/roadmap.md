# 开发路线图

项目负责本机专服的生命周期、配置、端口、日志和受访问限制的本地管理协议。地图玩法、资源下载与更新、玩家分配、Web 管理和跨机调度不在核心范围内。

## 阶段与验收

| 阶段 | 状态 | 目标 | 出口标准 |
| --- | --- | --- | --- |
| M0 运行基线 | 已完成 | 验证真实引擎与平台能力，确定实现前提 | 两平台分别进房、停止、重开；记录身份恢复、日志、端口及失败行为，见 [报告](validation/m0.md) |
| M1 最小闭环 | 已完成 | 模板校验、配置快照、显式端口、运行记录、本地 API 与 CLI | 两平台完成 create → status/operation → 进房 → restart → 再次进房 → stop；失败可定位，停止不产生重叠进程 |
| M2 管理可靠性 | 未开始 | 持久化、操作恢复、创建幂等、异常清理重试 | 管理端退出与崩溃后安全恢复；重复请求不重复开房；中断和损坏记录不引发误接管或误杀 |
| M3 多实例与回收 | 未开始 | 自动端口、资源冲突检测、日志与历史保留策略 | 至少两个实例同时运行并分别进房；一实例停止或失败不影响另一实例；文件和端口不冲突 |
| M4 双平台交付 | 未开始 | 构建包、平台模板、协议文档、启动器示例和独立 A2S 工具 | 干净环境按说明完成主要流程；双平台恢复验收；外部程序可调用，A2S 工具通过备份、冲突、幂等及写入失败验证 |

M1–M3 各阶段都需 Windows/Linux 实机验收；交叉编译和 CI 不能代替实际进房。M1 采用显式端口，自动分配由 M3 实现。

## 计划行为约束

以下是后续实现要求，并非当前已有功能：

- 模板、实例与运行代次分别建模。创建即请求启动；重启保留实例身份、最终生效配置和端口，确认旧进程退出后才能启动下一代。
- 主动停止不等待玩家状态；确认退出后回收活动实例及临时文件。启动失败或意外退出保留诊断，不自动拉起；已回收实例不能重启。
- 管理端退出保留专服，重新启动必须核验身份。同一 data-dir 只允许一个管理端写入，同实例变更操作串行。
- 进程存活、房间就绪、操作完成分别表达。变更请求返回可查询的操作 ID；受理成功不等于地图就绪，历史成功不代表当前仍可用。
- 模板与受支持 CLI 覆盖合并后保存快照；覆盖不回写模板，重启保留覆盖值，每代重新展开 cfg/log 路径。
- 默认 data-dir 位于核心程序旁，支持显式绝对路径；不可写时明确报错，不自动换目录。程序、工作目录和资源路径显式配置。
- 仅清理归属明确的生成文件；停止与清理结果分开。未确认进程退出时不释放分配，清理重试不能再次派生进程。
- 创建幂等契约在 M1 固定，M2 验证并发与崩溃可靠性。中断恢复须覆盖启动意图已写、进程已生但身份未写、停止已确认但回收未完成等窗口。
- TCP/UDP 与附加端口均进入诊断和冲突检查；M3 明确管理端离线时的日志容量边界。
- 本地接口限制访问用户，不提供远程管理端点。A2S 使用可选，但属于 M4 交付；普通启动不得隐式修改 gameinfo。

尚未确定的协议字段、持久化格式、清理重试策略和容量参数在对应阶段固定并验证，不以实验脚本接口作为正式 API。


## 后续扩展（不在当前交付范围）

未来同机独立节点控制器通过本地协议管理实例，核心不依赖控制器；平台与控制器不由本项目实现。后续可能增加针对实例和运行代次的受限控制台命令与可追踪原始输出增量读取。核心负责底层安全交互，控制器负责玩家与局内状态解析、查询频率和业务策略。

status_json 有手工执行线索，但自动发送、完整采集、输出归属和异常处理尚未验证，不能假定任意命令都有完整一问一答。本轮不实现该扩展，不预留接口，不新增远程端点；涉及启动兼容性或安全边界的后续影响须另行评估。
